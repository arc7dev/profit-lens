# PR #6 — Dashboard scale and formatting

**Branch:** `feature/dashboard-scale-and-formatting` → `develop` (merged 2026-08-19, squashed as `6976bdd`)
**Why this doc exists:** the PR shipped in 5 separate work sessions, each triggered by the same reviewer catching something the previous one missed (a layout bug, a wrong claim, an unmeasured assumption). The individual commit messages have the full reasoning for each fix, but nobody arriving fresh should have to reconstruct the shape of the whole thing from 5 commits' worth of prose. This is that reconstruction, written once.

## 1. What shipped

**Product table pagination.** Client-side: 25 rows/page, name search, sort — both search and sort run over the full result set before pagination slices it (sorting by lowest profit has to surface the single worst performer out of the whole catalog, not just whichever page was on screen). Deliberately **not** server-side: `ProfitLens_Profit_Engine::aggregate()` already computes every product's figures in one pass over the period's orders regardless of how many the UI will show — there's no per-product early exit to save server-side. Paginating server-side would only shrink the JSON payload, at the cost of a request per page/sort/search change plus a parallel PHP reimplementation of the same search+sort logic. See §2 below — that "payload size, not compute" framing turned out to matter more than expected, and now has its own issue (#8).

**Currency formatting** (`src/utils/currency.js`) — driven by WooCommerce's actual configured format (symbol, decimal/thousand separators, position), localized once via `window.profitLensData` (`class-assets.php`) since it isn't date-scoped. Replaced hardcoded `"$" + toLocaleString()` everywhere, which both mis-rendered numbers (`toLocaleString()` doesn't force a minimum decimal count, hence bugs like `$39,891.8`) and would have been flat wrong for a store using a comma decimal separator. Two fixed rules: KPI cards round to the dollar (0 decimals), table rows/totals and the cost breakdown always show 2.

**Cost coverage notice** — three severity tiers below "fully covered" (moderate/low/critical, on `revenue_covered_pct`) with escalating visual weight, copy that states the actual consequence ("...so profit may be overstated"), and a "Review products" link. `ProfitLens_Profit_Engine::aggregate()` gained a per-product `revenue_covered_pct` (same name/semantics as the period-level `cost_coverage.revenue_covered_pct`) — `has_cost` is kept as a derived boolean for back-compat. See §2 for why there's no "partial coverage" UI tier despite the more granular field existing.

**Product table horizontal overflow fix** — the table used to grow as wide as the longest product name in the catalog (up to 94 characters, real data), pushing Net Profit off-screen. Two dead-end approaches tried and rejected first (both documented in `dashboard.css` comments so nobody re-tries them):
1. `table-layout: fixed` + name column with no explicit width (meant to absorb leftover space) — fixed layout doesn't let a `max-width` on a cell shrink it back down once the column is sized; left a dead gap between the clamped name text and the next column on wide viewports.
2. `table-layout: fixed` + every column given a literal pixel width, table width set to their sum — fixed the gap, but the table stopped growing with its container, leaving a dead empty strip on wide viewports.

Final shape: **no `table-layout: fixed`** — the browser default (`auto`) is used instead, because `ProductTable` pages to 25 DOM rows at a time, so fixed layout's actual purpose (skip measuring content before laying out a huge table) doesn't apply here. The five numeric columns get real fixed pixel widths, sized off *measured* worst cases (wp-cli against the full-history catalog, then measured in the browser in the actual production font) — including a realistic all-time totals row (€/$500K+ range) and the "No cost set" chip, which is wider than any single-product currency figure. The name column gets `width: 100%` and absorbs the rest. Sticky name (left) / Net Profit (right) columns are the fallback for whatever horizontal scroll survives on a narrow admin viewport — verified against the real dashboard with the current column widths, both before and after every width change in this PR, not just once.

**Search box** — widened from a fixed 180px to `flex: 1` with a `350–400px` range (see §3.3 on why "1024/1280/1440 fit" wasn't a sufficient check), plus a magnifying-glass icon and a clear (×) button. Accessibility: real `<input type="search" aria-label="Search products">` (not a styled div, not relying on the placeholder as the accessible name), real `<button aria-label="Clear search">` next in Tab order, activates on Enter/Space, restores focus to the input after clearing. Found and fixed along the way: WP admin's own core CSS targets `input[type="search"]` with enough specificity to silently override the input's padding back to WP's 12px default — fixed by scoping the rule under its own wrapper rather than reaching for `!important` (unused elsewhere in this stylesheet).

## 2. Two non-obvious findings that will come up again

### Product cost is not versioned per order

`ProfitLens_Cost_Source_Cogs::get_product_cost()` → `WC_Product::get_cogs_total_value()` → `get_cogs_effective_value()` is a **pure function of the product's current state** — confirmed reading WooCommerce core's `abstract-wc-product.php` (~lines 2443–2519 in the version in this environment): no date, no order ID, anywhere in that call chain. Consequence: **editing a product's cost today retroactively rewrites the profit shown for every past period that product sold in**, not just future orders. This is a real product limitation, not a dashboard bug — filed as [issue #7](https://github.com/arc7dev/profit-lens/issues/7) with the mechanism and four solution options (per-order cost snapshot, a cost history table, disclosing the limitation instead of fixing it, or a lighter partial mitigation), **not decided yet**.

Direct fallout for this PR: since cost resolves from current state only, every line item for a given `product_id` within one `aggregate()` pass resolves to the *same* `unit_cost` — which means a single product's coverage in a single period can only ever be 0% or 100%, never partial. Confirmed two ways: reading the code (above), and empirically against all 1,297 products that have ever sold in the seeded dataset — **154 at 0%, 1,143 at 100%, zero in between**. This is why `revenue_covered_pct` exists in the engine (forward-compatible, in case cost resolution is ever versioned) but there's no third "partial coverage" chip tier in `ProductTable` — it would be dead code for a state that cannot occur today. See `Test_ProfitLens_Profit_Engine::test_cost_resolution_is_not_versioned_per_order()` — deliberately named/commented as a *known-limitation characterization*, not a desired-behavior assertion; if cost resolution ever changes to snapshot per order, that test *should* start failing (0.0 → 50.0), and the fix is to update the assertion, not treat the failure as a regression.

### The client-side pagination payload threshold is closer than "a few thousand products" sounded

Measured (not assumed) against the real seeded catalog (2,602 products, 1,297 ever sold): an all-time `/summary` response is **~780KB JSON, ~75KB gzipped**. Client-side compute (sort/filter/`JSON.parse`) stays under 10ms even synthetically pushed to 10,000 rows — it is not the bottleneck at any realistic catalog size. The actual constraint is **payload transfer time**, and it's not scoped to the table: `useSummary.js` fetches `kpis`/`chart`/`insight`/`cost_coverage`/`products` in one request, so a large `products` array delays the *entire* dashboard's first paint, not just the table's. This has its own issue now — [#8](https://github.com/arc7dev/profit-lens/issues/8) — separate from #7, since it's a different mechanism (network payload vs. a data-model limitation) with a different fix shape (split `products` into its own paginated request, not touch the cost model at all).

## 3. Patterns that worked here — worth repeating deliberately, not just as this PR's leftovers

1. **Measure against real data before deciding, not after a bug forces it.** wp-cli against the actual seeded catalog (not a synthetic small dataset) is what turned "table-layout: fixed feels right" into "table-layout: fixed is provably wrong here, ProductTable pages to 25 rows so its whole rationale doesn't apply" — and turned "a few hundred to a few thousand products should be fine" into a specific, defensible 780KB/75KB number with its own issue.
2. **`getBoundingClientRect()`/`getComputedStyle()` over reading a screenshot.** The "all three widths wrap to two lines" claim in an earlier round of this PR was wrong — reached by eyeballing a cropped screenshot instead of measuring exact `top` positions. Precise DOM measurement caught it immediately and for free.
3. **Sweep breakpoints/cases in small steps instead of checking only the 3-4 "representative" ones.** The header wrap's dead zone (search box shrinking to 225-365px between ~1080-1220px, well below its own intended minimum, while the header correctly stayed one line) only showed up because viewports were swept in ~20px steps across the gap between two known-good widths, instead of trusting that "fine at 1024, fine at 1280" meant fine in between. Binary checks (does it wrap: yes/no) miss continuous-value bugs like this one every time.
4. **Verify a scenario is reachable with real data before building UI for it.** The per-product "partial coverage" chip tier wasn't built — not because it was skipped, but because checking first (read the code, then confirm against all 1,297 real sold products) showed it's structurally impossible today. Building the tier anyway would have shipped a UI state with no real trigger and only synthetic test coverage.

Recommended instead: contextual to the moment someone actually edits a cost — e.g. near WooCommerce's own COGS field on the product edit screen — but that's a UX call for whoever picks up issue #7, not applied anywhere yet.
